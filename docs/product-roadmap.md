# DocLens-j 产品路线图

## 产品定位

DocLens-j 是文档解析基础设施，而不是个人账号系统或完整 SaaS 后台。
它的核心价值是作为业务流程、RAG 流程、OpenWebUI 集成或 Java/Spring Boot 宿主系统中的
OCR 与文档转文本组件，
稳定产出可消费的文本结果。

产品方向遵循三条边界：

- DocLens-j 负责文档接入、OCR/LLM 后处理、结果交付、调用归因和运行诊断。
- DocLens-j 通过调用方传入的分区键隔离数据，不接管终端用户登录。
- 个人账号、组织、RBAC、业务权限和最终用户授权由宿主系统或上游流程负责。

## 北极星指标

| 阶段 | 北极星指标 | 目标 |
| --- | --- | --- |
| 阶段 1 | 首次 OCR 成功时间 | 小于 5 分钟 |
| 阶段 2 | 批次调用方归因覆盖率 | 100% 批次可归因到接入方 |
| 阶段 3 | 下游流程可直接消费比例 | 超过 80% 的结果可直接进入下游流程 |

## 阶段 1：产品可试用闭环

### 目标

让新接入者在 5 分钟内完成一次真实 OCR，并拿到可以复制、下载或回调给下游系统的结果。

### 路线图

| 优先级 | 事项 | 用户价值 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 快速体验流程 | 降低首次使用门槛 | 用户能上传文件、查看状态、拿到结果 |
| P0 | 结果预览与下载 | 从“处理完成”变成“结果可用” | 支持 Markdown、TXT、JSON 结果下载 |
| P0 | 批次详情增强 | 提高排错效率 | 能看到页级进度、失败原因、回调状态 |
| P1 | 上传错误可理解 | 降低接入挫败感 | 后端结构化错误 detail 能清晰展示 |
| P1 | 5 分钟接入文档 | 提高试用转化 | 从启动服务到 OCR 成功有完整路径 |
| P1 | 示例文件和示例 curl | 降低验证成本 | README 或 docs 提供可复制示例 |

### 成功指标

- 首次 OCR 成功时间小于 5 分钟。
- 试用者无需阅读源码即可完成一次上传、查询、结果取用。
- 失败上传能显示可行动的错误原因。
- OCR 完成后，用户可以通过 Dashboard 或 API 获取结果文件。

## 阶段 2：接入方分区键与调用治理

### 目标

DocLens-j 不介入个人登录系统，而是通过请求发送 `X-Doclens-Key` 区分数据分区，让多个业务流程可以
可诊断、可归因地共用同一套文档解析能力。

### 身份边界

DocLens-j 接收的是 caller partition key，不是最终用户身份，也不是认证证据。
该 key 由上游系统选择粒度，可以代表项目、知识库、业务流程、团队或会话。
同 key 内共享数据，不同 key 之间隔离数据。

服务端不把 `X-Doclens-Key` 与后台名单比对，也不根据它证明“谁在调用”。
上游系统仍负责认证、授权、禁用、轮换和最终用户权限。DocLens 负责用这个 key
做数据隔离、调用归因、接口组限流和全局止损。

### 路线图

| 优先级 | 事项 | 用户价值 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 接入方分区键模型 | 区分不同共享边界 | 每个有效请求能解析出 caller partition |
| P0 | 缺失分区键拒绝 | 避免匿名共享空间 | 缺少或空白 `X-Doclens-Key` 的请求被拒绝 |
| P0 | 批次归因 | 方便排查和统计 | 批次、文档、回调都带调用方标识 |
| P1 | Dashboard 按调用方筛选 | 运维视角更清楚 | 能按调用方查看批次、失败、耗时 |
| P1 | 用量统计 | 支持容量规划 | 按调用方统计文件数、页数、成功率 |
| P1 | 分区键级限流 | 防止单一流程拖垮服务 | 可配置接口组 QPS 或突发限制 |
| P2 | 上游 key 策略示例 | 降低误用风险 | 文档说明按项目、知识库或团队选择粒度 |
| P2 | 调用审计事件 | 方便追责和排障 | 上传、删除、重试、回调重试可追踪 |

### 成功指标

- 100% 新批次能归因到接入方。
- 回调失败、上传失败、重试操作能定位到具体业务系统。
- 单个接入方异常流量不会拖垮所有调用方。
- 上游即使更换分区键，DocLens 的全局保护仍能提供跨 key 止损。

## 阶段 3：场景化与差异化

### 目标

从通用 OCR 能力升级为面向具体业务流的文档解析基础设施，让结果更容易进入 RAG、知识库、合同处理、
扫描件清洗等下游流程。

### 路线图

| 优先级 | 事项 | 用户价值 | 验收标准 |
| --- | --- | --- | --- |
| P0 | RAG 入库模式 | 贴合 OpenWebUI 和知识库场景 | 输出更适合切分、引用、入库 |
| P1 | OCR/LLM 评测集 | 建立质量信任 | 可比较不同节点或模型的成功率和耗时 |
| P1 | 结构化输出 | 提升业务可用性 | 支持章节、页码、表格、图片说明 |
| P1 | 场景模板 | 降低配置复杂度 | 提供合同、扫描件、论文、知识库等预设 |
| P2 | 质量评分 | 帮用户判断结果可信度 | 输出置信度、失败页、低质量页提示 |
| P2 | 接入示例项目 | 提高生态采用率 | 提供 OpenWebUI、RAG、Java 后端示例 |

### 成功指标

- 超过 80% 的完成结果可直接进入下游流程。
- 用户可以比较不同 OCR/LLM 配置的质量、耗时和失败率。
- 高频场景可以通过模板快速配置，而不是每次手工调参。
- 结果包含足够上下文，能支持引用、回溯和问题排查。

## 推荐执行顺序

1. 先完成阶段 1 的产品可试用闭环，确保上传、进度、结果、下载、错误说明可用。
2. 再完成阶段 2 的调用方归因，建立分区键、用量统计和筛选能力。
3. 最后推进阶段 3 的场景模板、RAG 输出、评测集和结构化结果。

## MVP 边界

第一版不做以下内容：

| 暂不做 | 原因 |
| --- | --- |
| 个人登录系统 | 不符合流程组件定位 |
| 用户表和角色表 | 账号与权限应由宿主系统负责 |
| 完整 RBAC | 当前只需要识别调用方，不需要管理终端用户 |
| 复杂计费系统 | 还没到商业化阶段 |
| 可视化工作流编排 | 容易变成另一个产品 |
| 复杂权限策略引擎 | 分区键归因和基础限流先够用 |
| 大而全的模板市场 | 先验证 2 到 3 个高频场景 |

## 风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
| --- | --- | --- | --- |
| 路线图过大导致实现分散 | 中 | 高 | 每次只把一个阶段拆成 OpenSpec 变更 |
| 调用方分区键被误解为用户登录 | 中 | 中 | 文档和接口命名统一使用 partition key |
| 分区键被伪造 | 中 | 高 | 按 key 限流，并保留全局保护作为跨 key 兜底 |
| 质量指标缺失导致用户不信任结果 | 中 | 高 | 阶段 1 先展示失败原因，阶段 3 增加评测和质量评分 |
| 场景模板过早泛化 | 中 | 中 | 先从 RAG、扫描件、合同等高频场景验证 |

## 下一步建议

下一步优先把阶段 1 收敛成独立 OpenSpec 变更：产品可试用闭环。
该变更应只覆盖首次体验、结果预览下载、批次详情增强和 5 分钟接入文档，
不提前引入阶段 2 或阶段 3 的实现范围。
